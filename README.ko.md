# gjl

**LLM 트래픽을 위한 자체 호스팅 정책 경계.**

아웃바운드 요청을 검사하고, 순서화된 정규표현식 규칙으로 민감한 콘텐츠를 차단하거나 디코딩된 요청 본문을 치환하며, 직접 운영하는 경계에서 제공자 자격 증명을 제어합니다.

## 빠른 설치 및 시작

명령어 하나로 gjl을 설치할 수 있습니다. 설치 프로그램이 사용자의 운영체제, CPU 아키텍처 및 디스플레이 환경을 자동으로 감지하고, `PATH` 환경 변수를 설정하며 해당 환경에 맞는 구성 요소를 설치합니다.

### Windows (PowerShell)

```powershell
irm https://gjl.io/install.ps1 | iex
```

*또는 `curl.exe` 사용:*
```powershell
curl.exe -fsSL https://gjl.io/install.ps1 | powershell -Command -
```

### macOS 및 Linux (curl)

```bash
curl -fsSL https://gjl.io/install.sh | sh
```

### CLI 전용 설치 (Desktop GUI 제외)

그래픽 데스크톱 환경이 있는 시스템에서 단독 `gjl` CLI만 설치하려는 경우:

* **Windows:**
  ```powershell
  $env:GJL_CLI_ONLY=1; irm https://gjl.io/install.ps1 | iex
  # 또는: & ([scriptblock]::Create((irm https://gjl.io/install.ps1))) -CliOnly
  ```
* **macOS 및 Linux:**
  ```bash
  curl -fsSL https://gjl.io/install.sh | sh -s -- --cli-only
  # 또는: curl -fsSL https://gjl.io/install.sh | GJL_CLI_ONLY=1 sh
  ```

> [!TIP]
> **헤드리스 및 서버 환경**: 디스플레이 서버가 없는 시스템(Linux 서버, 헤드리스 SSH 세션, Windows Server Core 등)에서는 설치 프로그램이 Flutter Desktop 다운로드를 자동으로 건너뛰고 단독 `gjl` CLI만 설치합니다.

### 실행

설치 직후 현재 터미널에서 다음 명령을 실행합니다:

- **데스크톱 GUI:**
  ```bash
  gjl gui
  ```
- **터미널 / 헤드리스:**
  ```bash
  gjl run
  ```

### gjl 업데이트

`gjl update`를 사용하여 설치된 구성을 최신 상태로 유지할 수 있습니다:

```bash
gjl update             # 로컬에 설치된 모든 구성 요소 업데이트 (CLI 및/또는 Desktop)
gjl update --cli-only  # gjl CLI만 업데이트
gjl update --gui-only  # Desktop GUI만 업데이트
gjl update --dry-run   # 다운로드 없이 업데이트 확인만 수행
```

수동 바이너리 다운로드 및 체크섬 검증은 [gjl 설치 및 검증 안내](docs/install.md)를 참고하세요.

## gjl의 활용 대상

- **보안을 중시하는 개인 및 조직**: 제공자에게 전송되기 전에 민감한 콘텐츠를 차단하거나 마스킹하고, 제공자 자격 증명을 직접 통제하는 경계에 보관하며, 필요한 경우 로컬 로그에 LLM 요청 및 위생화(sanitized)된 응답 사본을 기록하고자 하는 경우.
- **더 나은 LLM 응답 품질을 원하는 사용자**: 검사 가능한 요청 내에서 특정 워크플로에 맞춰 라우트 규칙을 통해 프롬프트 문구를 조정하거나 제공자가 지원하는 최신 모델로 변경하고자 하는 경우.
- **단일 LLM 제공자에 여러 계정을 보유한 개인 및 조직**: 자격 증명마다 별도의 라우트를 구성하고 클라이언트가 사용할 계정을 명시적으로 제어하고자 하는 경우. gjl은 계정 간 자동 부하 분산이나 장애 조치(failover)를 수행하지 않습니다.
- **다양한 코딩 에이전트 도구를 사용하는 개발자 및 팀**: 토큰 소비량을 추적하고, 예상 비용을 산출하며, 에이전트나 워크플로별 사용 패턴을 비교하고자 하는 경우.
- **팀 리드 및 관리자**: 공유 인프라 환경에서 팀원, 클라이언트 식별자 또는 자격 증명별로 토큰 사용량과 예상 비용을 집계하고자 하는 경우.

## gjl의 주요 기능

gjl은 코딩 에이전트, IDE 확장, 개발자 도구와 같은 LLM 클라이언트와 LLM 제공자 사이에서 동작합니다. 각 라우트는 Door 또는 Gate 중 하나에 속하며, 제공자 대상(target), 자격 증명 소스, 인바운드 인증 정책 및 마스킹 규칙을 자체적으로 소유합니다.

보호되는 요청 경로는 다음과 같습니다:

```text
디코딩된 본문
  → 차단 규칙 사전 검사
  → 순서화된 치환 규칙 적용
  → 자격 증명 경계
  → 제공자(Provider)
```

- **검사 대상 요청에서 일치하는 콘텐츠 차단 또는 치환**: 라우트 규칙은 제공자 인증 정보가 주입되기 전에 실행됩니다. 지원되는 디코딩된 HTTP 본문, 비압축 Connect JSON 페이로드, WebSocket 텍스트 메시지를 처리합니다. gRPC, Connect Protobuf 페이로드, 압축된 Connect 프레임, WebSocket 바이너리 메시지, 헤더, URL 경로 및 쿼리는 검사하지 않습니다. 규칙은 지원되는 경로에서 실제로 일치하는 콘텐츠만 보호합니다.
- **의도적인 요청 콘텐츠 조정**: 디코딩된 본문이 신뢰할 수 있는 구조를 가진 경우, 라우트는 프롬프트 문구 변경이나 모델 필드 재작성을 수행할 수 있습니다. 이는 민감 정보 보호에 사용하는 본문 규칙과 동일한 메커니즘입니다.
- **라우트를 통한 클라이언트 내 제공자 자격 증명 노출 방지**: 각 라우트에 자격 증명 소스를 하나씩 바인딩하고 송신 경계에서만 인증 정보를 교체함으로써, 업스트림 키가 클라이언트 설정에 남지 않도록 합니다.
- **Vault를 통한 페어링 릴레이 자격 증명 중개**: Vault는 LLM 트래픽을 프록시하지 않고 Door-Vault mTLS RPC를 통해 고정 API 키를 제공하고 OAuth 갱신 수명주기를 관리합니다. OAuth의 경우 릴레이는 필요할 때 짧은 수명의 액세스 토큰만 대여하며, 갱신 자격(refresh material)은 Vault 외부로 유출되지 않습니다.
- **토큰 사용량 및 예상 비용 추적**: gjl은 제공자가 보고한 프롬프트, 완료, 캐시 토큰 및 오프라인 USD 비용 환산액을 소유자 보호 원장에 기록합니다. 사용량 추적은 트래픽 로깅과 독립적이며, 프롬프트 본문이나 비밀 정보를 저장하지 않고 외부 모니터링 서비스를 필요로 하지 않습니다.
- **제공자 응답 본문 원형 보존**: 라우트 마스킹은 클라이언트에 전달되는 응답 본문을 절대 변조하지 않으며, 제한된 크기의 로컬 기록 사본만 위생화(sanitize)합니다. 릴레이는 응답 전달 시 필요한 HTTP hop-by-hop 헤더를 적절히 제거합니다.
- **트래픽 본문 없는 감사 메타데이터 전달**: 운영자는 이벤트 및 토큰 메타데이터를 수집하는 원격 감사 싱크(sink)를 구성할 수 있으나, 전송되는 정보는 메타데이터뿐입니다. 요청 및 위생화된 응답 본문은 명시적으로 삭제할 때까지 소유자 보호 로컬 감사 저장소에만 안전하게 보관됩니다.
- **벤더 클라우드 없는 독립 운영**: gjl에는 호스팅 제어 평면, 제품 계정, 로그인, 라이선스 서버, 기기 등록 또는 원격 측정(telemetry)이 없습니다.

## Door, Gate, Vault

Door, Gate, Vault는 별개의 에디션이 아니라 단일 데몬(`gjl run`으로 실행)이 동시에 수행할 수 있는 역할 기능입니다.

| 역할 | 목적 | 일반적인 배치 경계 |
| --- | --- | --- |
| **Door** | 로컬 릴레이 및 라우트 스위치보드 | 개발자 워크스테이션 또는 로컬 서버 |
| **Gate** | 공유 TLS 게이트웨이, 조직 정책 경계 및 자격 증명 주입 지점 | 사용자 또는 조직이 운영하는 네트워크 경계 |
| **Vault** | API 키를 제공하고 갱신 정보를 소유하는 자격 증명 브로커 | 전용 자격 증명 관리 경계 |

지원되는 배포 경로는 다음과 같습니다:

```text
LLM 클라이언트 --> Door --------------------> 제공자(Provider)
LLM 클라이언트 --> Door --> Gate -----------> 제공자(Provider)
LLM 클라이언트 ------------> Gate -----------> 제공자(Provider)
                   Door <-> Vault
                 자격 증명 RPC 전용
```

Vault는 프롬프트, 소스 코드, 일반 제공자 요청 및 원시 제공자 응답을 일절 수신하지 않습니다.

## gjl 다운로드

운영체제와 CPU 아키텍처에 맞는 파일을 [GitHub Releases](https://github.com/gjl-io/gjl/releases)에서 다운로드할 수 있습니다.
알파 릴리스는 **Pre-release**로 표시됩니다. 설치 전에 릴리스 노트를 확인하고 [다운로드 파일 검증](docs/install.md)을 수행하세요. 데스크톱 번들에는 일치하는 `gjl` 바이너리가 포함되어 있습니다.

초기 사전 출시 버전에는 Windows/macOS 플랫폼 신뢰 게시자 서명 및 macOS 공증이 포함되어 있지 않습니다. 따라서 Windows MSIX 패키지는 제공되지 않으며, macOS에서는 항목별로 **확인 없이 열기(Open Anyway)** 승인이 필요할 수 있습니다. 정확한 신뢰 한계와 검증 방법은 설치 문서를 참고하세요.

| Windows Arm64 | — | `gjl-windows-arm64.exe` |
| Linux x64 | `gjl-linux-amd64.deb` 또는 `gjl-linux-amd64.zip` | `gjl-linux-amd64` |
| Linux Arm64 | `gjl-linux-arm64.deb` 또는 `gjl-linux-arm64.zip` | `gjl-linux-arm64` |

| macOS Apple silicon | `gjl-darwin-arm64.pkg` 또는 `gjl-darwin-arm64.zip` | `gjl-darwin-arm64` |

### 데스크톱 지원 언어

데스크톱 앱은 8개 인터페이스 언어를 지원합니다. 시스템 로케일을 따르며, 지원되는 언어와 일치하지 않으면 영어를 기본값으로 사용합니다. 핵심 제품명인 gjl, Door, Gate, Vault는 모든 언어 환경에서 영문 표기를 유지합니다.

### 알파 프로필 호환성 안내

알파 릴리스는 후속 알파 버전과의 상태 파일 호환성을 보장하지 않습니다. 최신 알파 버전을 시험할 때는 새로운 프로필을 사용하세요. gjl은 이전 프로필을 자동으로 삭제하거나 변환하지 않습니다. 프로필을 변경하기 전에 필요한 설정, 자격 증명, TLS 인증서, 페어링 기록, 감사 로그 및 사용량 데이터를 명시적으로 백업하거나 내보내세요. 복구에 대비해 이전 버전 바이너리와 백업 상태를 보관하는 것을 권장합니다.

## 시작하기

데스크톱 번들에는 `gjl` CLI와 데몬이 함께 포함되어 있습니다. 데스크톱 앱은 소유자 보호 IPC를 통해 로컬 데몬을 관리합니다. 입력된 자격 증명을 전달받아 데몬에 전송하며, 데몬이 영구 저장소를 소유하고 보안 정책을 시행합니다.

gjl을 통해 LLM 트래픽을 라우팅하려면 세 가지 핵심 요소가 필요합니다:

1. **라우트(Route)**: Door 또는 Gate를 대상으로 업스트림 제공자 타깃, 마스킹 규칙 및 인증 정책을 정의합니다. 기본적으로 클라이언트 자격 증명은 변경 없이 그대로 통과(passthrough)되며, 트래픽 로깅과 마스킹 감사는 꺼져 있습니다.
2. **일치하는 리스너(Listener)**: 라우트에 바인딩된 클라이언트 진입점입니다. 워크스테이션용 Door(로컬 루프백) 또는 공유 네트워크 접근용 Gate(TLS)가 사용됩니다. (리스너는 동일한 역할의 라우트에만 바인딩됩니다.)
3. **LLM 클라이언트의 Base URL**: 코딩 에이전트, IDE 확장 또는 개발자 도구가 해당 리스너의 주소를 가리키도록 설정합니다.

### 데스크톱 환경 설정

데스크톱 앱에서는 설정 마법사를 통하거나 수동으로 구성할 수 있습니다:

- **빠른 설정 (마법사)**: 상단 대시보드 HUD에서 **+ (추가)** 버튼을 클릭합니다. **이 기기에서 사용**을 선택하면 1단계와 2단계가 한 번에 처리되어, 자격 증명 passthrough가 적용된 로컬 Door 라우트 및 루프백 리스너가 자동으로 생성됩니다. **팀과 공유**를 선택하면 공유 **Gate** 엔드포인트 또는 **Vault** 자격 증명 브로커를 설정하는 단계로 안내됩니다.
- **수동 설정**: **라우팅** 화면을 열어 라우트와 리스너를 개별적으로 생성하고 검사할 수 있습니다.

> [!TIP]
> **제공자 자격 증명 관리 (선택 사항):** gjl은 기본적으로 인바운드 클라이언트 자격 증명을 저장하지 않고 제공자에게 그대로 전달합니다. gjl이 경계에서 제공자 자격 증명을 직접 관리, 주입 또는 중개하도록 하려면 라우트에서 참조하기 전에 별도의 **자격 증명** 카탈로그에 자격 증명을 먼저 등록하세요.

### 헤드리스 또는 CLI 관리

헤드리스 환경이나 명령줄에서는 번들된 `gjl` 바이너리를 사용하여 데몬을 실행하고 엔터티를 직접 관리할 수 있습니다:

```console
$ gjl run
```

다른 터미널 창에서:

```console
$ gjl status
$ gjl doctor
$ gjl route --help
$ gjl listener --help
$ gjl --help
```

CLI와 Desktop은 macOS/Linux에서는 Unix 도메인 소켓을, Windows에서는 네임드 파이프를 통해 통신합니다. 데몬이 소유한 설정, 자격 증명 또는 감사 저장소 파일을 직접 수정하지 않습니다.

## 라우트 치환 규칙 활용

`replace`(치환)는 단순한 비밀 정보 마스킹뿐만 아니라 요청 본문 전반을 제어하는 규칙입니다. 범위가 좁게 지정된 라우트는 특정 작업의 성능을 향상시키는 것이 입증된 경우 `an apple`을 `the green apple`로 변경할 수 있습니다. 또한 제공자가 최신 모델을 지원하지만 클라이언트 도구가 아직 이를 업데이트하지 않은 경우, 클라이언트의 요청 모델을 `gpt-5.6-sol`에서 `gpt-6-sol`로 교체할 수도 있습니다. 단, 치환 규칙으로 제공자가 지원하지 않는 모델을 사용할 수 있게 하거나 헤더/URL에만 포함된 모델명을 변경할 수는 없습니다.

**실제 디코딩된 본문에서 일치 패턴을 선택하세요.** 규칙을 활성화하기 전에 해당 정규표현식 패턴이 의도한 텍스트만을 고유하게 식별하는지 검토해야 합니다. 단순한 모델명이나 일상적인 단어는 프롬프트, 코드, 예제 또는 다른 필드에서도 나타날 수 있습니다. 라우트의 트래픽 로깅을 일시적으로 켜고, 데스크톱의 활동 탭이나 `gjl audit query`, `gjl audit bodies`, `gjl audit body-save` 명령을 통해 로컬 요청 본문(`body`) 구조를 확인한 뒤 패턴을 설계하세요. 헤더 값은 본문 치환 대상이 아닙니다. 클라이언트의 원본 본문을 확인해야 하는 경우 치환 규칙을 활성화하기 전에 트래픽 로깅을 수행하세요. 감사 요청 본문에는 치환이 적용된 후 제공자에게 전송된 내용이 기록됩니다. 트래픽 로깅은 기본적으로 꺼져 있으며, 명시적으로 삭제할 때까지 본문을 로컬에 보관하므로 보관 정책을 고려하여 사용해야 합니다. 별도 파일로 저장된 본문은 별도로 삭제해야 합니다.

예를 들어, 캡처된 한 WebSocket `response.create` 요청 본문이 공백 없는 압축 JSON(`{"type":"response.create","model":"gpt-6-sol",...}`) 형태이고 모델 필드가 쉼표로 둘러싸여 있다면, 구버전 모델을 전송하는 클라이언트를 위해 다음과 같이 라우트 규칙을 작성할 수 있습니다:

```json
{
  "id": "upgrade-model",
  "mode": "replace",
  "pattern": ",\"model\":\"gpt-5\\.6-sol\",",
  "replacement": ",\"model\":\"gpt-6-sol\","
}
```

이 예시는 특정 구조에 맞춘 것입니다. 서식이 지정된(pretty-printed) JSON이나 다른 위치에 있는 `model` 필드에는 일치하지 않습니다. 해당 클라이언트의 요청 본문을 직접 확인하고 구조가 다르면 규칙을 조정하세요. gjl은 Go RE2 정규표현식 문법을 사용하며, 원본 디코딩 본문에 대해 모든 차단(block) 규칙을 먼저 검사한 후 라우트 순서에 따라 치환(replace) 규칙을 적용합니다. 규칙은 클라이언트로 전송되는 제공자 응답 본문을 절대 변조하지 않으며, 로컬에 저장되는 응답 사본만 위생화합니다.

민감한 텍스트를 마스킹하는 규칙의 경우, 클라이언트 측 AI에게 아웃바운드 요청 콘텐츠가 네트워크 경계에서 치환된다는 사실을 시스템 프롬프트 등으로 안내하는 것이 효과적일 수 있습니다. 비밀 정보 자체는 노출하지 않고 플레이스홀더와 예상되는 동작만을 명시합니다. 제공자는 이미 치환된 요청을 수신하므로, 해당 요청 내의 지시문으로 원본 텍스트를 복원할 수는 없습니다. `<GJL_MASKED>`를 사용하도록 구성된 라우트의 경우, 에이전트 지침에 다음과 같이 작성할 수 있습니다:

> gjl replaces matching sensitive text with `<GJL_MASKED>` before the provider receives the request. Keep that placeholder intact; do not try to reconstruct its original value.

규칙을 수정한 후에는 실제 요청을 통해 검증하고, 임시 트래픽 로깅을 끈 다음 불필요한 감사 이벤트를 명시적으로 삭제하세요.

캡처된 본문 구조로부터 규칙 특이성을 검증하고 작성하는 워크플로는 [라우트 치환 규칙 스킬](skills/route-replacements/SKILL.md)을 참고하세요.

## 보안 모델

- 라우트는 Door 또는 Gate 중 하나에 엄격히 귀속됩니다. Door 리스너는 Door 라우트에만, Gate 리스너는 Gate 라우트에만 바인딩되며 단일 라우트를 역할 간에 공유할 수 없습니다.
- 마스킹 규칙은 라우트에 소속됩니다. 모든 차단(block) 규칙은 치환이 실행되기 전에 원본 디코딩 요청을 검사하며, 이후 치환 규칙이 등록 순서대로 적용됩니다.
- 제공자 인증은 본문 마스킹과 독립적으로 처리되며, 코딩 에이전트의 이름이 아닌 제공자의 유선 규격에 따라 결정됩니다.
- 제공자 요청 및 자격 증명은 gjl 개발자가 운영하는 인프라를 일절 거치지 않습니다.
- Door는 로컬 퍼스트로 동작합니다. 원격 또는 공유 환경에서는 TLS 및 CIDR 제어가 적용된 Gate를 사용해야 합니다. 엄격한 엣지 접근 통제 없이 Door 엔드포인트를 외부에 노출해서는 안 됩니다.
- 로컬 트래픽 본문은 자동으로 만료되지 않습니다. 삭제는 필터링되거나 전체 확인을 거치는 명시적 관리 작업입니다.
- Gate는 관측된 클라이언트(Observed Client) 메타데이터(출발지 IP, 제한된 User-Agent 및 보조 클레임, 인증 HMAC 지문 등)를 소유자 보호 로컬 저장소에 최선형(best-effort)으로 기록할 수 있습니다. 이는 검증된 인간 신원이 아니며, 감사 이벤트를 삭제해도 해당 저장소가 자동으로 지워지지 않습니다.
- 운영자가 구성한 원격 감사 싱크는 관측된 클라이언트/행위자 식별자 및 제공자 보고 토큰 사용량 등의 메타데이터를 수신할 수 있으나, 트래픽 본문이나 원시 관측 신호는 일절 수신하지 않습니다. 보존 기간 및 원격 접근을 설정할 때 이러한 메타데이터의 민감성을 고려해야 합니다.
- 업데이트 확인은 자문(advisory) 목적입니다. 릴리스 데몬은 이 GitHub 저장소의 공개 태그만 확인하며, 업데이트를 자동으로 다운로드하거나 설치하지 않습니다.

리스너를 호스트 외부에서 접근 가능하도록 설정하기 전에 [Gate를 통한 원격 접근 안내](docs/remote-exposure.md)를 반드시 숙지하세요.

## 소스 코드를 비공개로 유지하는 이유

우리는 AI의 발전으로 기본적인 릴레이 구현이 쉬워짐에 따라, 전체 구현을 공개하여 얻는 실익이 줄어들었다고 판단합니다. gjl은 민감한 LLM 트래픽과 자격 증명을 다루며, 소스 코드 전체를 공개할 경우 공격자가 취약점을 더 쉽게 탐색할 수 있는 위험이 있습니다. 따라서 보안 설계의 일환으로 제품 소스 코드를 비공개로 유지합니다.

실행 중인 gjl 프로세스가 어디로 연결되는지는 오픈 소스 Python 도구인 [연결 관측 도구](docs/connection-observer.md)를 통해 직접 확인할 수 있습니다. 이 도구는 라우트 업스트림, Gate/Vault 연결, 알려진 OAuth 서버, GitHub 연결을 식별하여 레이블을 부여하며, 확인되지 않은 대상은 사용자가 검토할 수 있도록 `UNKNOWN`으로 표시합니다. 안전성을 임의로 판정하지 않으며 요청 본문이나 자격 증명을 읽지 않습니다.

gjl을 실행한 후 저장소 루트에서 다음을 실행합니다:

```sh
python -m pip install -r tools/requirements.txt
python tools/observe_connections.py --duration 600
```

## 프로젝트 원칙 및 보장

gjl은 로컬 및 운영자 소유 권한 원칙을 중심으로 설계되었습니다:

- 벤더가 운영하는 백엔드나 런타임 서비스가 없습니다.
- 제품 계정, 로그인, 유료 기능 잠금 또는 기기 등록이 없습니다.
- 원격 측정(telemetry)이 없습니다.
- 업데이트 확인 시 제공자 요청, 자격 증명, 설정, 감사 데이터가 전송되지 않습니다.
- 업데이트 자동 설치나 롤백을 수행하지 않습니다.

유일하게 발생하는 벤더 측 네트워크 통신은 공개 GitHub 저장소에 대한 인증 없는 태그 조회, 사용자가 명시적으로 `gjl update`를 실행할 때 수행하는 공식 릴리스 다운로드, 그리고 Desktop GUI에서 사용자가 요청할 때 브라우저로 릴리스 페이지를 여는 것뿐입니다.
