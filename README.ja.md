# gjl

**LLM トラフィックのためのセルフホスト型ポリシー境界。**

外部へのリクエストを検査し、順序付けられた正規表現ルールでコンテンツの遮断やデコード済みリクエスト本文の書き換えを行い、自身が管理する境界でプロバイダー認証情報を厳格に制御します。

## クイックインストール＆スタート

単一のコマンドで gjl をインストールできます。インストーラーが OS、CPU アーキテクチャ、ディスプレイ環境を自動検出し、`PATH` を構成して適切なコンポーネントをセットアップします。

### Windows (PowerShell)

```powershell
irm https://gjl.io/install.ps1 | iex
```

*または `curl.exe` を使用:*
```powershell
curl.exe -fsSL https://gjl.io/install.ps1 | powershell -Command -
```

### macOS & Linux (curl)

```bash
curl -fsSL https://gjl.io/install.sh | sh
```

### CLI のみインストール（デスクトップ GUI を除外）

グラフィカルデスクトップ環境のあるシステムで、スタンドアロンの `gjl` CLI のみをインストールしたい場合:

* **Windows:**
  ```powershell
  $env:GJL_CLI_ONLY=1; irm https://gjl.io/install.ps1 | iex
  # または: & ([scriptblock]::Create((irm https://gjl.io/install.ps1))) -CliOnly
  ```
* **macOS & Linux:**
  ```bash
  curl -fsSL https://gjl.io/install.sh | sh -s -- --cli-only
  # または: curl -fsSL https://gjl.io/install.sh | GJL_CLI_ONLY=1 sh
  ```

> [!TIP]
> **ヘッドレスおよびサーバー環境**: ディスプレイサーバーが存在しないシステム（Linux サーバー、ヘッドレス SSH セッション、Windows Server Core など）では、インストーラーは Flutter Desktop のダウンロードを自動的にスキップし、スタンドアロンの `gjl` CLI のみをインストールします。

### 実行

インストール後、現在のターミナルで直ちに実行できます:

- **デスクトップ GUI:**
  ```bash
  gjl gui
  ```
- **ターミナル / ヘッドレス:**
  ```bash
  gjl run
  ```

### gjl のアップデート

`gjl update` を使用して、インストールされたコンポーネントを最新の状態に保ちます:

```bash
gjl update             # ローカルにインストールされた全コンポーネントを更新 (CLI および/または Desktop)
gjl update --cli-only  # gjl CLI のみ更新
gjl update --gui-only  # Desktop GUI のみ更新
gjl update --dry-run   # ダウンロードを行わずに更新を確認
```

手動でのバイナリダウンロードおよびチェックサム検証については、[インストールと検証ガイド](docs/install.md)をご覧ください。

## 想定される利用者

- **セキュリティを重視する個人やチーム**: プロバイダーに到達する前に機密コンテンツを遮断またはマスキングし、プロバイダー認証情報を自己管理下の境界にとどめ、必要に応じて LLM リクエストおよび無害化されたレスポンスの複製をローカルログに記録したい方。
- **より良い LLM の出力品質を求める方**: 検査可能なリクエストにおいて、特定のワークフローに合わせてルートルールでプロンプト文を調整したり、プロバイダーがサポートする新しいモデルへ書き換えを行いたい方。
- **同一プロバイダーに複数のアカウントを持つ組織**: 認証情報ごとに独立したルートを設定し、クライアントが使用するアカウントを明示的に制御したい方。gjl はアカウント間の自動負荷分散やフェイルオーバーを行いません。
- **複数のコーディングエージェントツールを使用する開発者やチーム**: トークン消費量を追跡し、概算コストを算出し、エージェントやワークフロー間での利用傾向を比較したい方。
- **チームリーダーや管理者**: 共有インフラストラクチャ全体で、メンバー、クライアント識別子、認証情報ごとにトークン消費量と概算コストを集計したい方。

## gjl の機能概要

gjl は、コーディングエージェント、IDE 拡張機能、開発者ツールなどの LLM クライアントと LLM プロバイダーの間で動作します。各ルート（Route）は Door または Gate のいずれかに属し、プロバイダーターゲット、認証情報ソース、インバウンド認証ポリシー、マスキングルールを独自に保持します。

保護されたリクエストの処理フロー:

```text
デコード済み本文
  → 遮断ルールの事前チェック (Block precheck)
  → 順序付けられた置換ルールの適用 (Ordered replacements)
  → 認証情報境界 (Credential boundary)
  → プロバイダー (Provider)
```

- **検査対象リクエスト内の一致コンテンツの遮断または置換**: ルートルールはプロバイダー認証情報が注入される前に実行されます。サポートされているデコード済み HTTP 本文、非圧縮 Connect JSON ペイロード、WebSocket テキストメッセージに対応します。gRPC、Connect Protobuf ペイロード、圧縮された Connect フレーム、WebSocket バイナリメッセージ、ヘッダー、URL パスやクエリは検査しません。ルールはサポート対象パスで実際に一致したコンテンツのみを保護します。
- **意図的なリクエスト内容の調整**: デコード済み本文が安定した構造を持つ場合、プロンプトのフレーズ書き換えやモデル名の差し替えが可能です。これは機密情報のマスキングと同じルール機構を使用します。
- **ルート経由での認証情報秘匿**: 各ルートに単一の認証情報ソースを紐付け、送信境界でのみ認証情報を付与することで、クライアントの設定に上流の API キーを保持させません。
- **Vault によるペアリング済みリレーへの認証情報仲介**: Vault は LLM トラフィックをプロキシせず、Door-Vault 間の mTLS RPC 経由で静的 API キーを提供し、OAuth リフレッシュのライフサイクルを管理します。OAuth の場合、リレーは必要に応じて有効期間の短いアクセストークンのみを借用し、リフレッシュ材料が Vault の外部に出ることはありません。
- **トークン使用量と概算コストの追跡**: プロバイダーが報告したプロンプト、完了、キャッシュトークンとオフラインの USD コスト換算額を、所有者保護された台帳に記録します。使用量追跡はトラフィックログとは独立しており、プロンプト本文やシークレットを保存せず、外部の監視サービスも不要です。
- **プロバイダーレスポンス本文の無改変維持**: ルートマスキングはクライアントへ返送されるレスポンス本文を改変しません。サイズ制限されたローカル記録用コピーのみを無害化（sanitize）します。リレーはレスポンス転送時に必要な HTTP ホップバイホップヘッダーを適切に除去します。
- **トラフィック本文を含まない監査メタデータの外部転送**: 管理者はイベントおよびトークンメタデータを収集するリモート監査シンクを構成できますが、送信されるのはメタデータのみです。リクエストおよび無害化されたレスポンス本文は、明示的に削除されるまで所有者保護されたローカル監査ストアにのみ保持されます。
- **ベンダークラウド不要の完全な自律運用**: gjl にはベンダー運用のコントロールプレーン、アカウント、ログイン、ライセンスサーバー、デバイス登録、テレメトリは一切ありません。

## Door、Gate、Vault

Door、Gate、Vault は個別のエディションではなく、単一のデーモン（`gjl run` で起動）が同時に提供できる役割機能です。

| 役割 | 目的 | 一般的な配置境界 |
| --- | --- | --- |
| **Door** | ローカルリレーおよびルートスイッチボード | 開発者のワークステーションまたはローカルサーバー |
| **Gate** | 共有 TLS ゲートウェイ、組織ポリシー境界、認証情報注入ポイント | ユーザーまたは組織が運用するネットワーク境界 |
| **Vault** | API キーを提供しリフレッシュ材料を保持する認証情報ブローカー | 専用の認証情報管理境界 |

サポートされているデプロイ構成:

```text
LLM クライアント --> Door --------------------> プロバイダー
LLM クライアント --> Door --> Gate -----------> プロバイダー
LLM クライアント ------------> Gate -----------> プロバイダー
                     Door <-> Vault
                    認証情報 RPC のみ
```

Vault はプロンプト、ソースコード、通常のリクエスト、生レスポンスを受信することは一切ありません。

## はじめに

デスクトップバンドルには `gjl` CLI およびデーモンが含まれています。デスクトップアプリは所有者保護された IPC 経由でローカルデーモンを管理します。入力された認証情報はデーモンへ渡され、デーモンが永続ストレージを管理しポリシーを適用します。

gjl を経由して LLM トラフィックをルーティングするには、3 つの要素が必要です:

1. **ルート (Route)**: Door または Gate に対して、アップストリームプロバイダーのターゲット、マスキングルール、認証ポリシーを定義します。デフォルトではクライアントの認証情報はそのまま通過（passthrough）し、トラフィックログおよびマスキング監査は無効です。
2. **一致するリスナー (Listener)**: ルートにバインドされたクライアントの接続受付窓口です。ワークステーション用の Door（ローカルループバック）または共有ネットワーク用の Gate（TLS）を使用します。（リスナーは同一の役割のルートにのみバインドできます。）
3. **LLM クライアントの Base URL**: コーディングエージェント、IDE 拡張機能、開発ツールの接続先をそのリスナーのアドレスに向けます。

### デスクトップでのセットアップ

デスクトップアプリでは、ウィザードまたは手動で構成できます:

- **クイックセットアップ (ウィザード)**: ダッシュボード上部の HUD で **+ (追加)** をクリックします。**このデバイスで使用する** を選択するとステップ 1 と 2 が一度に完了し、認証情報パススルーが設定されたローカル Door ルートおよびループバックリスナーが作成されます。**チームと共有する** を選択すると、共有 **Gate** エンドポイントまたは **Vault** 認証情報ブローカーの構成へ案内されます。
- **手動セットアップ**: **ルーティング** 画面を開き、ルートとリスナーを個別に作成・確認します。

> [!TIP]
> **プロバイダー認証情報の管理（任意）:** デフォルトでは、gjl はクライアントから渡された認証情報を保存せずプロバイダーに透過転送します。gjl 側で認証情報を一元管理・注入・仲介したい場合は、ルートで参照する前に独立した **認証情報** カタログへあらかじめ登録してください。

### ヘッドレスまたは CLI での管理

ヘッドレス環境やコマンドラインからは、同梱の `gjl` バイナリを用いてデーモンを実行し、直接管理できます:

```console
$ gjl run
```

別のターミナルで:

```console
$ gjl status
$ gjl doctor
$ gjl route --help
$ gjl listener --help
$ gjl --help
```

CLI と Desktop は macOS/Linux では Unix ドメインソケット、Windows では名前付きパイプを使用します。デーモンが所有する設定、認証情報、監査データベースファイルを直接読み書きすることはありません。

## ルート置換ルールの活用

`replace`（置換）は単なる機密マスキングだけでなく、リクエスト本文全般を制御するルールです。範囲を狭く絞り込んだルートであれば、特定タスクの精度向上が確認されている場合に `an apple` を `the green apple` に書き換えることができます。また、プロバイダーが新しいモデルを公開しているもののクライアントツール側が未対応の場合に、リクエストモデルを `gpt-5.6-sol` から `gpt-6-sol` に差し替えることも可能です。ただし、利用不可能なモデルを利用可能にしたり、ヘッダーや URL にのみ含まれるモデル名を変更することはできません。

**実際のデコード済みリクエスト本文に基づいてパターンを設計してください。** ルールを有効化する前に、その正規表現パターンが意図したテキストのみを一意に識別できるか検討してください。単体のモデル名や日常的な単語は、プロンプト、ソースコード、用例、その他のフィールド内にも出現する可能性があります。ルートのトラフィックログを一時的に有効にし、デスクトップのアクティビティ画面または `gjl audit query`、`gjl audit bodies`、`gjl audit body-save` を使ってローカルに取得されたリクエスト本文（`body`）の構造を確認した上でパターンを作成してください。ヘッダー値は本文置換の対象外です。元のリクエスト本文を確認したい場合は、置換ルールを有効にする前にトラフィックログでキャプチャしてください。監査ログのリクエスト本文には置換適用後にプロバイダーへ送信された内容が記録されます。トラフィックログはデフォルトでオフになっており、明示的に削除するまでローカルに保持されるため、保管方針を考慮して利用してください。別ファイルに保存した本文は個別に削除する必要があります。

例えば、キャプチャされた WebSocket `response.create` のリクエスト本文がスペースのない JSON（`{"type":"response.create","model":"gpt-6-sol",...}`）であり、モデルフィールドがカンマで囲まれている場合、古いモデル名を送信するクライアント向けに以下のルート置換ルールを設定できます:

```json
{
  "id": "upgrade-model",
  "mode": "replace",
  "pattern": ",\"model\":\"gpt-5\\.6-sol\",",
  "replacement": ",\"model\":\"gpt-6-sol\","
}
```

この例は特定の JSON 形式に依存しています。改行された JSON や別位置の `model` フィールドには一致しません。クライアントのリクエスト本文を実際に確認し、必要に応じてルールを調整してください。gjl は Go RE2 正規表現構文を採用しており、デコードされた元の本文に対してすべての遮断（block）ルールを評価した後に、登録順で置換（replace）ルールを適用します。ルールがクライアントへ返送されるレスポンス本文を変更することはなく、ローカルに記録されるコピーのみを無害化します。

機密テキストのマスキングルールを適用する場合、クライアント側 AI のシステムプロンプト等で「送信リクエストはネットワーク境界で置換される」旨を伝えておくと効果的です。シークレットそのものは記述せず、プレースホルダーと期待される挙動のみを伝えます。プロバイダーには置換後のリクエストが渡るため、リクエスト内の指示によって元テキストを復元させることはできません。`<GJL_MASKED>` を使用するルートの場合、エージェントへの指示例は次のようになります:

> gjl replaces matching sensitive text with `<GJL_MASKED>` before the provider receives the request. Keep that placeholder intact; do not try to reconstruct its original value.

ルール変更後は実際のリクエストで検証を行い、一時的なトラフィックログをオフにし、不要になった監査イベントを明示的に削除してください。

キャプチャされた本文構造からルールの特異性を検証・作成するワークフローについては、[ルート置換スキル](skills/route-replacements/SKILL.md)を参照してください。

## セキュリティモデル

- ルートは Door または Gate のいずれかに厳密に帰属します。Door リスナーは Door ルートにのみ、Gate リスナーは Gate ルートにのみバインド可能であり、単一のルートをロール間で共有することはできません。
- マスキングルールはルートが所有します。置換が行われる前に、すべての遮断ルールが元のデコード済みリクエストを検証し、その後置換ルールが定義順に実行されます。
- プロバイダー認証は本文マスキングとは独立して処理され、コーディングエージェントの名称ではなくプロバイダーの通信仕様に基づいて選択されます。
- プロバイダーリクエストおよび認証情報が gjl 開発者のインフラを経由することは一切ありません。
- Door はローカルファーストです。リモートまたは共有アクセスを行う場合は、TLS および CIDR 制御を備えた Gate を使用してください。厳格なエッジアクセスコントロールなしに Door エンドポイントを外部公開してはなりません。
- ローカルのトラフィック本文は自動的に期限切れになりません。削除はフィルター指定または確認を伴う明示的な管理操作です。
- Gate は、観測されたクライアント（Observed Client）メタデータ（送信元 IP、制限された User-Agent、補助クレーム、認証 HMAC フィンガープリントなど）を所有者保護されたローカルストアにベストエフォートで記録できます。これらは検証された人間アイデンティティではなく、監査イベントを削除してもこの独立ストアは自動削除されません。
- 管理者が構成したリモート監査シンクはメタデータ（クライアント識別子、プロバイダー報告のトークン使用量など）を受信できますが、トラフィック本文や生の観測シグナルを受信することはありません。保持期間やリモートアクセスを設定する際は、これらのメタデータの機密性を考慮してください。
- 更新チェックはアドバイザリ（通知のみ）です。リリースデーモンは本 GitHub リポジトリの公開タグのみを読み取り、アップデートを自動的にダウンロードまたはインストールすることはありません。

リスナーをホスト外部に公開する前に、[Gate によるリモートアクセス](docs/remote-exposure.md)を必ずお読みください。

## ソースコードを非公開とする理由

AI の進化により基本的なリレーの実装が容易になった現在、実装コード全体を公開するメリットは小さくなったと考えています。gjl は機密性の高い LLM トラフィックや認証情報を扱うため、完全なソースコードの公開は攻撃者が潜在的な弱点を探索することを容易にしてしまう懸念があります。そのため、セキュリティ設計の一環として製品コードを非公開としています。

実行中の gjl プロセスがどこに接続しているかは、オープンソースの Python ツールである [接続オブザーバー](docs/connection-observer.md) で確認できます。ルートのアップストリーム、Gate/Vault 接続、既知の OAuth サーバー、GitHub を自動で識別してラベル付けし、未特定の接続先は `UNKNOWN` として表示します。安全性の主観的判断は行わず、リクエスト本文や認証情報を読み取ることもありません。

gjl を起動後、リポジトリルートで以下を実行します:

```sh
python -m pip install -r tools/requirements.txt
python tools/observe_connections.py --duration 600
```

## リポジトリの構成

本リポジトリは gjl の公式な公開配布拠点であり、以下を含みます:

- 公式リリースのダウンロードおよび正規のバージョンタグ
- 公開された運用・セキュリティドキュメント
- 独自の安全判断を行わずに可視ネットワーク接続を識別するオープンソースの [ローカル接続オブザーバー](docs/connection-observer.md)
- サポートされたワークフローの安全な構成を支援するエージェントスキル
- CLI、Desktop、製品ドキュメントへ案内する AI タスクマップ [`llms.txt`](llms.txt)

現在利用可能なエージェントスキル:

- [`skills/gjl-operations`](skills/gjl-operations/SKILL.md) — インストール済み CLI の確認、Desktop 画面の案内、ローカル管理を支援。
- [`skills/route-replacements`](skills/route-replacements/SKILL.md) — 観測されたリクエスト構造（機密テキスト、プロンプト語句、モデルフィールド）に基づく本文のブロック・置換ルールの設計支援。
- [`skills/remote-exposure`](skills/remote-exposure/SKILL.md) — Door-Gate 間の mTLS ペアリングおよびリモートアクセスの境界検証。

## プロジェクトの保証

gjl はローカルおよびオペレーター主権の原則に基づいて設計されています:

- ベンダーが運営するバックエンドやランタイムサービスはありません。
- 製品アカウント、ログイン、有料機能ロック、デバイス登録はありません。
- テレメトリ（遠隔測定）の収集はありません。
- 更新チェック時にプロバイダーリクエスト、認証情報、設定、監査データが送信されることはありません。
- アップデートの自動インストールや自動ロールバックは行いません。

ベンダー側とのネットワーク通信は、公開 GitHub タグの認証なし照会、ユーザーが明示的に `gjl update` を実行した際の公式リリースアセットのダウンロード、および Desktop GUI からユーザーの要求に応じてブラウザで公開リリース一覧ページを開くことのみです。
